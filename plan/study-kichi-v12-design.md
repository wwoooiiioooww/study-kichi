# スタディきち v12+ 設計書(Claude Code引き継ぎ用)

> 本書は機能追加4件+リリースロードマップの設計。実装時は必ず「スタディきち開発スキル(SKILL.md)」を併読し、絶対原則(入力させたら負け/承認ゲート/自己申告は報酬非連動/migrate必須/段階納品)に従うこと。
> 対象コード: 単一 `index.html`(v11) + PWA一式。状態は `S`、現メンバー `P()`、`save()`/`render()`/`openModal()`。

## 推奨実装順

1. **v12: ロケットOP + きせかえ + 特別ミッション**(軽量・独立・すぐ喜ばれる)
2. **v13: 同期 Step A(ポイント台帳化+マージ基盤) → Step B(Firebase+家族コード)**(別チャットで合意済みの設計)
3. **v14: リベンジノート + AIレポート連携**(写真を含むため、同期の後が望ましい※注)

※注: ノート写真はIndexedDB(端末内・同期/バックアップ対象外)。ノート本文はJSONに含める。複数端末運用が始まっているため、テキストデータを増やす機能は同期基盤の後に入れる方が事故が少ない。ただし独立性は高いので順序入替は可。

## 機能1: 🚀 ロケットオープニング

### 仕様
- アプリ起動(ページロード)時、1回だけスプラッシュを表示: 空グラデ背景 → ロケット(絵文字🚀またはアイコン流用SVG)が画面下から上へ約1.1秒で飛ぶ。雲2つ+尾の炎。
- 画面タップで即スキップ。`prefers-reduced-motion: reduce` なら表示しない。
- 表示順: ロケットOP → launchGate(だれがつかう?) → ホーム。
- 実装: `#splash` オーバーレイ(z-index 500) + CSS keyframes。`render()` 前に挿入し、animationend または1.3sタイマーで remove。

### テスト観点
- reduced-motion時スキップ / タップスキップ / OP後にPINゲートが正常表示 / 2回目のrender()で再表示されない

## 機能2: 🎨 背景きせかえ

### 仕様
- テーマ6種: `sky`(既定・所持済), `sakura`(所持済), `sunset`, `night`, `sea`, `forest`。
- 各テーマ = CSS変数セット(--sky-bg, --sky-deep, ヘッダーgradient3色, --card は白維持)。`night` はインク色コントラストに注意(文字色は変えず背景を暗くしすぎない: 紺〜藍の範囲)。
- データ: `p.theme='sky'`, `p.ownedThemes=['sky','sakura']`(メンバーごと)。migrateで付与。
- 入手: ⭐こうかんじょに常設「🎨きせかえ」セクション(システム品・親のpoolとは別枠)。各300pt。購入で ownedThemes に追加(重複購入不可)。
- 切替: せってい画面「🎨きせかえ」カード。所持テーマはタップで即適用、未所持はグレー+「こうかんじょで300pt」表示。
- 適用: `applyTheme()` が :root にCSS変数を設定。起動時とswitchProfile時に呼ぶ(メンバーごとに違うテーマ)。

### 設計意図
ポイントの恒常的なシンクを増やす(経済の健全化)。子どもが自分で触ってよい数少ない「せってい」項目として楽しさを担保。

### テスト観点
- 購入→残高減算→所持反映→適用 / 未所持タップで購入誘導 / プロフィール切替でテーマが切り替わる / migrate(旧データにtheme/ownedThemes付与)

## 機能3: 🎯 パパ・ママからの特別ミッション

### データ
```js
p.missions=[{id:'ms..',title,pts, due:{type:'today'|'week'|'date',date:null|'YYYY-MM-DD'},
 status:'open'|'claimed'|'approved'|'expired', createdTs, claimedTs:null, approvedTs:null, ack:false}]
```
migrate: `p.missions=[]`。

### フロー
1. **作成(パパ・ママモード)**: 新セクション「🎯特別ミッション」。入力=タイトル/ポイント(数値,min1)/期限(きょう中・こんしゅう中(週土曜まで)・日付指定)。一覧に現役ミッション(open/claimed)表示、削除可。
2. **子ども側(ホーム)**: openなミッションをカード表示「🎯パパ・ママからの特別ミッション」: タイトル+『+50pt』+期限(『きょう中!』『7/25まで』)。ボタン「できた!」→ status=claimed。
3. **承認**: パパ・ママモードの承認まちに「🎯ミッション承認まち」行(セッション/ボーナスと同並び)。承認→ status=approved, `p.points+=pts`。却下→ statusをopenに戻す(再挑戦可。削除したければ親が削除)。
4. **達成演出**: 承認後、子どもが次にホームを開いたとき「🎉ミッションたっせい! +50pt」カード(confetti、ackボタンで消える)。
5. **期限切れ**: 表示時に判定し open→expired(グレー表示3日後に自動非表示)。ペナルティなし。親は期限延長(=dueを編集)で復活可。

### 原則との整合
- 報酬は承認ゲート必須(claimed→承認→付与)。スロットを経由しない固定ポイント(臨時収入)。
- せっていバッジ件数に claimed 数を合算。
- 将来のポイント台帳化(同期Step A)で「ミッション: +50」を取引として記録する前提のコメントを残す。

### テスト観点
- 作成→ホーム表示→できた!→承認→加点→達成カード→ack / 却下でopenに戻る / today期限が翌日expired / week期限が週土曜23:59まで有効 / migrate

## 機能4: 🔁 リベンジノート(復習コーナー)

### 位置づけと命名
- 常設の「よわみ・まちがいノート」。週次自動の「リベンジリスト」(ボスバトル由来・教科単位)とは別物だが同じ世界観。リストは従来通り、ノートはきろくタブに常設カードとして新設。

### データ
```js
p.notes=[{id:'n..',ts,subj,text,photoId:null,status:'open'|'done',doneTs:null,src:'manual'}]
```
- 写真はIndexedDB(既存 putPhoto/getPhoto を流用、compressImage適用)。**バックアップJSON・将来の同期の対象外**(UIに明記)。
- migrate: `p.notes=[]`。save()容量超過ハンドラの対象外(本文は軽量、写真はIDB)。

### UI
- **きろくタブ最上部**に「🔁リベンジノート」カード: フィルタチップ(のこってる/クリアずみ/ぜんぶ, 既定=のこってる) + 一覧(教科バッジ・本文1〜2行・📷サムネ・チェックボックス) + 「＋きろくする」。
- **追加/編集モーダル**: 教科チップ(単一選択)+テキストarea(🎤音声入力: 既存toggleVoiceを対象要素引数化して流用)+📷(カメラ/ファイル)。保存で一覧へ。
- **セッション終了モーダル**に導線: 「きろくしたよ!」確認モーダルに「🔁まちがいをノートにのこす」ボタン(タップでノート追加モーダルへ)。
- チェック: タップで done(打ち消し線)。誤タップ戻し可。

### AI連携
- **AIレポート**: info に `リベンジノート:{のこり:{算数:2,国語:1}, 今週クリア:3, 最近ののこり:[本文先頭20字×最大5件(テキストのみ)]}` を追加。プロンプトの💡ヒント指示に「リベンジノートののこりを踏まえ、らいしゅうの作戦に入れる具体案を1つ含める」を追記。
- **さくせん会議カード**: のこりがある場合のみ1行ヒント「🔁ノートののこり: 算数2・国語1 → 作戦にいれる?」。

### 報酬設計(合意済み方針)
- **記録には報酬ゼロ**(自己申告の正直さ保護。ゴミ記録による経済汚染とAI材料の劣化を防ぐ)。
- **克服に週次ボーナス**: その週(日〜土)に done にした件数が3件以上 → `grantBonus(週,'notes','🔁リベンジノート3件クリア ボーナス',false)`(承認制・週1回上限は grantedフラグで自動担保)。doneを外して付け直しても再付与されないこと(週のgranted参照)。
- ポイント直付与はしない。既存の週次ボーナス群と同じ「🎁承認でスロット+1」に統一。

### テスト観点
- 追加(文字のみ/写真つき/音声入力)→一覧→チェック→フィルタ / 週3件クリアでpendingボーナス1回のみ / チェック外し→再チェックで二重付与なし / レポートinfoにノート情報が入る / セッション終了からの導線 / migrate

## リリース(ストア配信)ロードマップ

### 前提整理
- 現状の配布(URL+ホーム画面追加)は友達家庭βに十分。ストアは「発見性・信頼感」のための次段階。
- **一般公開の最重要課題はストア審査ではなく、AIの提供方式**。見知らぬ家庭にAPIキー取得は求められない → 自前の中継サーバー(利用量制限・未成年向け安全フィルタ・運用費)が必須。

### 段階
1. **いま**: URL配布で友達家庭β。フィードバック収集。
2. **同期+家族コード完成後**: クローズドβ拡大。プライバシーポリシー/利用規約のドラフト作成。
3. **AI中継サーバー**(Cloudflare Workers or Firebase Functions + 自前キー + レート制限 + 子ども向けセーフティ)。
4. **Google Play**: Bubblewrap(TWA)でラップ。開発者登録$25(買切)。子ども向け=ファミリーポリシー準拠(データ安全性フォーム、広告なし、収集データ申告)。審査往復込みで実作業数日+待ち。
5. **App Store**: Capacitorでラップ(Mac+Xcode必要、$99/年)。「Webの皮」却下リスク(ガイドライン4.2)があるため、プッシュ通知・ネイティブ共有などネイティブ価値を足してから申請推奨。iOSはPWA(Safari追加)運用の継続でも当面可。

### 判断基準(急がない理由)
- ストアに出す=不特定多数のサポート・レビュー対応・審査対応の固定費を負う。同期とAI提供方式が固まる前に出すと、初期レビューで信頼を失いやすい。
- 目安: 「友達家庭5〜10軒が同期込みで1か月安定運用」をPlay申請のゲートにする。
